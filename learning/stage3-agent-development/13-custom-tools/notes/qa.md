# 13 - 自定义工具开发 费曼笔记

## 一、信息抽象

**它解决什么问题？**

防止 LLM 上下文爆炸。通过渐进式曝光（先给摘要+总数，需要更多时再按引导深入查询），用多轮循环弥补上下文窗口限制。

**反面案例**

naive_search 把匹配文档全文倾泻给 LLM——100 篇 × 500 字 = 50000 token，LLM 被淹没事，无法聚焦关键信息。

**我能用它做什么？**

- 搜索工具：返回 top N + 总数 + 缩小范围的引导，而非全量结果
- 数据库查询：返回前 5 行 + 总行数 + "指定条件可查看更多"
- 日志分析：先返回错误类型分布，LLM 选择具体类型后再返回详细堆栈

## 二、状态反馈

**它解决什么问题？**

让 Agent 精确把控工具运行状态——多少成功、多少失败、每个失败的原因。Agent 拿到这些信息后能在下一轮循环针对性地处理失败项，而非一无所知地重试。

**反面案例**

batch_process 只返回 "处理完成"，Agent 不知道有 5 项失败，无法决定是否需要重试。

**我能用它做什么？**

- 批量数据处理：逐项报告进度 + 成功/失败统计 + 后续建议
- 文件上传：已上传 X/Y，失败原因列表，建议重试或跳过
- 并发 API 调用：聚合各请求状态，报告部分失败时的降级方案

## 三、错误恢复接口

**它解决什么问题？**

保证 LLM 能准确且精确地调用工具。好的错误信息让 LLM 根据反馈做出合理调整，而非靠盲猜。错误信息必须包含：发生了什么 + 为什么 + 可以尝试什么。

**反面案例**

`return "Error"` —— LLM 不知道哪里错了，只能盲猜修正方向。

**我能用它做什么？**

- API 参数验证：缺少参数 → 指出缺少哪个 + 给出示例
- 端点路由：未知端点 → 列出所有可用端点及用途
- 数据查询：未找到结果 → 列出已知数据范围，引导缩小查询

## 核心领悟

> 同样的 LLM，不同的 agent 差距为什么那么大？因为 70% 的工作是工具工程。工具返回的信息质量直接决定 LLM 的决策质量——LLM 是大脑，工具是眼睛和手。眼睛看不清，大脑再强也做不出正确决定。

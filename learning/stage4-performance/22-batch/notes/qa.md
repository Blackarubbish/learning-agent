# 批处理优化 (Batching) — 费曼笔记

## 一、它解决什么问题？

每次 API 调用都有固定的网络往返开销（RTT + 连接建立 + 序列化/反序列化）。当需要处理 N 条数据时，逐条调用意味着支付 N 次往返开销，而实际服务端计算时间的占比很低。

实验数据：30 条文本做 Embedding，逐条 7.7s（30 次 API），批量 0.69s（1 次 API），加速 11 倍。省下的 7 秒不是服务端算得更快，而是省掉了 29 次网络往返。

批处理的核心价值：**用一次网络往返完成 N 条数据的处理，让固定开销从 N 次降为 1 次**。

## 二、核心原理（用类比解释）

**Embedding 批处理 = 大巴拼车**：一群人（N 条文本）挤一辆大巴（一次 HTTP 请求），目的地相同，一起到达。坐满发车，分摊油费（RTT）。

**LLM batch = 多辆出租车同时出发**：一群人各叫一辆车（N 次 HTTP 请求），同时发车（线程池并发），各自独立到达。总时间 ≈ 最慢那辆的行程，而非所有出租车行程之和。

技术层面：
- `embeddings.embed_documents(texts)` 在服务端一次计算 N 个向量，N 条文本打包在一个 HTTP body 里
- `llm.batch(prompts)` 内部用 `ThreadPoolExecutor` 并发调用 `invoke()`，每个 prompt 仍是独立的 API 请求
- 前者减少请求次数，后者让请求等待时间重叠——两个维度正交，可以叠加使用

## 三、反面案例 —— 如果没有它，会发生什么？

用 bs=1 逐条处理 1 万条文档的向量化：

- 每次请求耗时 ≈ 250ms（含 RTT），总耗时 ≈ 10000 × 0.25s = 2500s ≈ 42 分钟
- 其中服务端实际计算时间可能只有 30ms/条，即总共 300s = 5 分钟
- 也就是说 42 分钟里有 37 分钟是网络往返开销，CPU/GPU 几乎空闲

用 batch_size=50 分批处理：10000/50 = 200 次 API 调用，总耗时 ≈ 200 × 0.35s = 70s ≈ 1 分钟。同样的硬件，吞吐量提升 35 倍。

**批处理不仅影响吞吐，还影响成本**——API 按 token 计费时网络开销不直接收费，但超时重试、连接池耗尽、rate limit 触发都会间接增加成本。

## 四、我能用它做什么？（3 个具体场景）

1. **知识库批量向量化**：ch04 的知识库导入，N 个文档切片一次性调用 `embed_documents()`，而非逐片调用。10 万字的文档可能切成 200 个 chunk，batch 后只需 1 次 API。

2. **RAG 评估批量打分**：ch11 的 RAG 评估管线中，用 `llm.batch()` 同时对多条 RAG 回答做 Faithfulness / AnswerRelevancy 评判。原本 20 条答案串行评估要 60s，batch 后 5s。

3. **缓存预热**：ch20 学到的缓存策略有个前提——高频查询需要提前生成好答案写入缓存。预热流程是：取 TOP 100 FAQ → `embed_documents(faqs)` 批量向量化 → `llm.batch(prompts)` 并发生成标准答案 → 写入精确缓存 + 语义缓存。批处理让预热从分钟级降到秒级。

## 五、和已有知识的关联（指向 CONCEPT_MAP.md）

## 六、我还困惑的地方（留白后续补充）

1. **生产环境的批处理策略** — 实验中是固定 batch_size 的静态切片，生产中是自适应微批（时间窗口 + 最大批次双阈值）、Continuous Batching（推理引擎层动态插入新请求）、优先级分级（在线请求跳过队列 vs 离线导入攒大批次）。下一章 vLLM 会深入 Continuous Batching 的实现细节。

2. **llm.batch() 的适用边界** — 适合多个相互独立的 LLM 调用（批量评估、批量分类、生成候选答案），不适合有依赖关系的调用链（Agent 多轮循环、工具调用链、流式输出）。在有 `asyncio` 环境的项目中，`llm.abatch()` 比 `llm.batch()` 更高效（用 `asyncio.gather` 替代线程池）。

3. **批量 vs 异步的选择** — 什么时候用批处理，什么时候用异步，什么时候两者叠加？单次请求能处理的就批处理（Embedding），不能的就异步并发（LLM 对话）。两者叠加的场景：多个批处理任务同时跑（如同时预热多个知识库）。

## 关键 API 速查

| 用途 | API | 机制 |
|------|-----|------|
| Embedding 批处理 | `embeddings.embed_documents(texts)` | API 级合并，N 条文本 → 1 次 HTTP |
| LLM 并发调用 | `llm.batch(prompts)` | 框架级并发，N 个 prompt → N 次 HTTP（线程池） |
| 控制并发度 | `llm.batch(prompts, config={"max_concurrency": 5})` | 限制同时发起的请求数 |
| LLM 异步批处理 | `await llm.abatch(prompts)` | 异步版 batch，内部用 asyncio.gather |

# 缓存优化 — LLM 响应缓存

## 一、它解决什么问题？

两个维度：
- **用户体验**：缓存命中后响应时间从 4-5 秒（等 LLM API）降到 0 秒，用户感知不到等待
- **成本控制**：相同问题不再重复调用 LLM API，直接省掉 token 费用

本质是"空间换时间"——用内存存储换网络往返。

## 二、核心原理

### Cache-Aside 模式
```
查询缓存 → hit? → YES → 返回缓存
              → NO  → 调 LLM → 写缓存 → 返回结果
```

### 精确缓存 vs 语义缓存

| 维度 | 精确缓存 | 语义缓存 |
|------|---------|---------|
| 匹配方式 | SHA256(prompt) 字符完全匹配 | embedding 余弦相似度 |
| 成本 | 免费（本地 hash） | 每次查询调 embedding API |
| 误命中风险 | 零 | threshold 调不好会误匹配 |
| 适用场景 | 高频重复查询、FAQ、固定模板 | 同义改写、多语言变体 |

### 为什么不全用语义缓存？

1. 每次查语义缓存都要调 embedding API（额外耗时+成本），精确缓存 SHA256 是本地计算的
2. 有误命中风险（"怎么学" vs "怎么删"在语义空间可能很近）
3. 生产环境用**两级缓存**：精确 → 语义 → LLM

### 技术细节
- redis 只能存 str/bytes/int/float，AIMessage 对象需转 `.content` 再存
- fakeredis 纯内存实现，API 完全兼容 redis-py，零依赖适合开发测试

## 三、反面案例 —— 如果没有它？

100 个用户问同一个问题 100 次，就调 100 次 LLM API，每次 4-5 秒网络 I/O。19 章 profile 的结果白做了。

## 四、我能用它做什么？

1. 高频 FAQ 系统：FAQ 查询全部精确缓存，用户秒级响应
2. 代码助手：相同错误信息/相同代码问题，第一次查完 LLM 后缓存，后续用户免费命中
3. 客服系统：大量重复问题，缓存后 API 成本从线性增长变成常数级

## 五、和已有知识的关联

- 19章 cProfile：profile 出 LLM API 是瓶颈 → 缓存直接消除这个瓶颈
- 向量检索（FAISS/Milvus）：语义缓存的 embedding 相似度匹配本质和向量检索是一个原理
- Agent Memory（16章）：记忆是给 LLM 上下文，缓存是跳过 LLM 调用——两个不同层次

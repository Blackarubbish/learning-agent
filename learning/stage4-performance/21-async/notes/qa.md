# 异步处理 (Async) — 费曼笔记

## 一、它解决什么问题？

同步编程在处理 I/O 操作（网络请求、文件读写）时，CPU 会阻塞等待，直到操作完成才能继续执行下一条指令。如果系统需要处理多个请求，同步模式下只能串行排队——每个请求等待前一个完成后才被处理，CPU 大部分时间处于空闲状态。

异步机制通过协程和事件循环，在 I/O 等待时主动让出 CPU 控制权，切换到其他协程继续执行。当 I/O 操作完成后，事件循环再恢复之前的协程。这使得**多个 I/O 操作的等待时间可以重叠**，从而在单线程内实现并发，无需引入多线程的锁和同步开销。

## 二、核心原理（用类比解释）

异步模型类似餐厅里的一个服务员服务多桌客人：

- 服务员（事件循环）接到 A 桌点单后，把订单交给厨房，不会站在厨房门口干等
- 在厨师做菜的等待时间里，服务员去服务 B 桌、C 桌
- 哪桌的菜做好了（I/O 完成），服务员就回到哪桌继续服务

关键区别：**同步是多请几个服务员（多线程），异步是让一个服务员在等待间隙切换任务（事件循环）**。

技术层面，`await` 不是"阻塞等待"而是"挂起并让路"——协程执行到 `await` 时将自己挂起，事件循环调度其他就绪的协程运行。当挂起的操作完成，协程回到就绪队列等待恢复。

## 三、反面案例 —— 如果没有它，会发生什么？

> 实验数据：5 个并发查询，同步 40.64s vs 异步 14.61s，加速比 2.8x

同步模式下，每个请求串行执行，总耗时等于每个请求耗时之和。5 个查询各需要約 8 秒 I/O 等待，总耗时约 40 秒——其中约 35 秒 CPU 处于空闲状态。

异步模式下，5 个请求几乎同时发出，I/O 等待时间重叠，总耗时约 14 秒。并发数越高，同步和异步的差距越大。

**但需注意**：异步不加速单个任务。如果只有一个查询，同步和异步耗时相同——因为没有其他协程可切换，"让路"没有意义。

## 四、我能用它做什么？（3 个具体场景）

1. **Web 服务端并发处理**：FastAPI 本身就是异步框架，多个用户同时请求时，服务端可以在等待数据库查询/LLM API 返回期间处理其他请求，提升 QPS
2. **批量数据采集/调用**：需要调用多个外部 API 获取数据时（如同时查询 10 个数据源），用 `asyncio.gather` 并发请求，等待时间从 Σ 降到 max
3. **Agent 多工具并发调用**：FC Agent 循环中，如果 LLM 决定同时调用多个工具（如同时搜索知识库和调用外部 API），这些工具调用可以并发执行，而非串行等待

## 五、和已有知识的关联（指向 CONCEPT_MAP.md）

- [[19-profiling]] — cProfile 发现了 LLM API 占 90%+ 时间的瓶颈，sync→async 正是解决这个 I/O 等待问题
- [[20-redis-cache]] — 缓存消除**重复查询**的 I/O，async 让**非重复查询**的 I/O 等待时间重叠；两者互补，共同降低延迟

## 关键 API 速查

| 同步 | 异步 | 说明 |
|------|------|------|
| `llm.invoke(msgs)` | `await llm.ainvoke(msgs)` | LLM 调用 |
| `httpx.post(url, ...)` | `async with httpx.AsyncClient() as c: await c.post(url, ...)` | HTTP 请求 |
| `vectorstore.similarity_search(q)` | `await vectorstore.asimilarity_search(q)` | 向量检索 |
| `for q in queries: run(q)` | `await asyncio.gather(*[run(q) for q in queries])` | 并发执行 |

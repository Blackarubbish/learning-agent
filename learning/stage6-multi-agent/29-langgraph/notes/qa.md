# LangGraph 费曼笔记

## 一、它解决什么问题？

把 LLM 应用的控制流从「散落在代码里的 while/if」变成「显式的图结构」。

具体解决三件事：
1. **流程可见**：节点和边一目了然，新人看代码就知道应用会怎么走
2. **状态可控**：所有中间状态都保存在 State 里，方便审计、回放、断点续跑
3. **人工介入容易**：可以在任意节点前暂停等人确认，再接着跑

## 二、核心原理（用类比解释）

LangGraph 像一个**工厂流水线控制面板**：

- **State** = 流水线上的托盘，装着当前物料
- **Node** = 工位，每个工位对托盘做一件事
- **Edge** = 传送带，固定把托盘送到下一个工位
- **ConditionalEdge** = 分拣器，根据托盘上的标签决定送往哪条支线
- **Checkpoint** = 每个工位拍的照片，机器坏了可以从照片处恢复

以前写 Agent 是手写 `while` 循环控制流水线；用 LangGraph 是先把流水线画出来，再填每个工位做什么。

## 三、反面案例 —— 如果没有它，会发生什么？

1. **流程藏在代码细节里**：读代码时很难一眼看出「失败后会怎样」「会不会无限循环」
2. **状态散落在各处**：LLM 输出、工具返回、中间变量混在一起，排查问题困难
3. **难以恢复和审计**：程序中途崩溃后，不知道跑到哪一步，只能从头再来
4. **团队协作成本高**：每个人写 Agent 循环的方式不同，代码风格差异大

## 四、我能用它做什么？（3 个具体场景）

1. **复杂客服系统**：先路由问题类型 → 检索知识库 → 判断是否需要人工 → 生成回复 → 人工审核后发出
2. **自动化运维 Agent**：接收告警 → 查询日志 → 分析根因 → 尝试修复 → 验证结果 → 不行就升级给人
3. **多步 RAG 流水线**：查询改写 → 多路检索 → Rerank → 判断上下文是否足够 → 生成答案 → 反思校验

## 五、和已有知识的关联

- 与 ReAct 循环的关系：
  ReAct 是「思考 → 行动 → 观察」的循环，LangGraph 的 StateGraph 把这个循环画成图：`agent` 节点负责思考，`tool` 节点负责行动，`ConditionalEdge` 判断是继续循环还是结束。

- 与 Swarm / AutoGen / CrewAI 的关系：
  Swarm 的 Handoff、AutoGen 的 GroupChat、CrewAI 的 Process 都在解决「多个 Agent 怎么协调」。LangGraph 不替代它们，而是提供一个更底层的图结构，让你可以用 StateGraph 自己实现 Swarm/AutoGen/CrewAI 的协调模式。

## 六、我还困惑的地方

- 问题：LangGraph 在哪个节点调用 LLM？
- 回答：LLM 调用发生在某个 Node 内部。StateGraph 本身只负责调度，不调用 LLM。你需要在节点函数里写 `llm.invoke(...)` 或 `llm.ainvoke(...)`。哪个节点调用 LLM、调用几次，完全由你设计的图决定。

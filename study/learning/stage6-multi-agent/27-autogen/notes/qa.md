# AutoGen GroupChat

## 一、它解决什么问题？

当多个 Agent 需要协作时，**谁来决定下一轮到谁发言**？

AutoGen GroupChat 把这个问题抽象成可插拔的 `SpeakerSelector`：
- 简单场景用 `RoundRobinSelector` 固定轮询
- 复杂开放场景用 `LLMSelector` 根据上下文动态分派

## 二、核心原理（用类比解释）

想象一个会议有三类角色：研究员、分析师、写手。

- **RoundRobin** 像主持人按座位顺序点名，简单可控，适合流程明确的会议
- **LLMSelector** 像真正的会议主持人，会根据讨论内容判断「现在该谁补充」，适合开放式研讨

所有 Agent 共享同一个 `history`，所以每个人都能看到完整上下文，像同一张会议桌。

## 三、反面案例 —— 如果没有它，会发生什么？

如果所有工作都交给一个 Agent：

1. **上下文爆炸**：查资料、做分析、写总结全堆在一个窗口里
2. **角色混淆**：不同角色的 system prompt 互相干扰，输出风格不稳定
3. **难以调试**：出了问题不知道是该补充资料、该分析、还是该重写
4. **token 成本高**：长上下文导致每次调用都更贵

## 四、我能用它做什么？（3 个具体场景）

1. **标准化流程**（RoundRobin）
   需求评审 → 产品文档 → 技术方案 → 代码开发 → 测试验收

2. **调研报告生成**（LLMSelector）
   用户提一个开放性问题，协调员动态决定「先查资料」「再分析」「最后总结」

3. **多角色 Code Review**
   安全审查员 → 性能审查员 → 可维护性审查员按顺序或动态 review 同一段代码

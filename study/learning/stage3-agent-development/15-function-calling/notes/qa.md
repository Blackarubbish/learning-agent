# Function Calling 实战

## 一、它解决什么问题？

Function Calling 把 Agent 的工具调用从"文本解析"升级到"结构化协议"。
- ReAct 模式下，工具定义是 prompt 中的一段文本，模型输出自由文本，开发者用正则在文本中抠 Action/Action Input——嵌套 JSON、特殊字符、格式偏差都会导致解析失败。
- FC 用 JSON Schema 定义工具参数（标准的类型+枚举约束），模型被训练输出 `tool_calls` token，LangChain 直接解析为结构化 dict，**100% 解析成功率**。
- 代码从 ReAct 的 ~100 行（循环+解析器）降到 ~30 行（bind_tools + ToolMessage 循环）。

## 二、核心原理（用类比解释）

- **ReAct** 像是你给助手一张纸条："遇到数学题就写'计算: 表达式'"，然后你用人眼识别纸条上的字。如果助手字迹潦草（格式偏差），你就读不懂。
- **Function Calling** 像是你给助手一个标准化表格，上面有"工具名"下拉框和"参数"输入框。助手填表（输出 tool_calls token），你直接读表——不存在"读不懂"的问题。

## 三、反面案例 —— 如果没有它，会发生什么？

没有 FC，开发者需要用正则解析 LLM 的自由文本输出来提取工具调用信息：
- 嵌套引号（如 `'hello "world"'`）会截断 JSON 解析
- 模型输出格式偏差（多一个换行、少一个引号）导致解析失败
- 每次新增工具都要同步更新解析规则
- 不支持并行调用（一次只能调一个工具）
- 维护成本和 bug 率随工具数量线性增长

本章实验 6 证实了这一点：复杂参数下 FC 1 步完成，ReAct 直接跑满 5 步失败。

## 四、我能用它做什么？（3 个具体场景）

1. **生产环境 Agent**：工具数量多、需要长期维护、调用可靠性要求高——FC 的 JSON Schema 定义和 100% 解析率是刚需。
2. **需要并行调用的场景**：用户问"查A的股价和B的天气"，FC 可以一次返回两个 tool_calls，减少轮次和延迟。
3. **需要精确控制调用行为的场景**：`tool_choice="required"` 确保关键流程一定触发工具，`tool_choice="none"` 让模型先分析再决定——不需要 hack prompt。

## 五、和已有知识的关联

- **第 12 章 ReAct**：FC 是 ReAct 的进化版——同样的 Agent 循环模式（思考→行动→观察），但工具调用方式从文本解析升级为结构化协议。
- **第 13 章自定义工具**：工具工程原则（信息抽象、错误保留、描述即接口）在 FC 中同样适用，且 FC 的 JSON Schema 让工具描述更加标准化。
- **第 14 章 SQL 工具**：SQL Agent 的工具定义也可以用 FC 格式，`db_schema` 和 `db_query` 的入参校验更严格。

# 17 - Agent 错误处理与反思机制 — 费曼笔记

## 一、它解决什么问题？

Agent 调用工具时会失败（超时、参数错误、无权限等）。如果不处理，LLM 面对裸错误信息会困惑、胡乱重试、消耗 token 甚至得出错误结论。错误处理机制让 Agent 能**理解失败原因并自我修正**，从而提高单步可靠性，间接提高长任务整体成功率。

核心公式：单步可靠性 95% → 20 步后只剩 36%。错误处理通过让每一步"失败后能修正"来打破这个指数衰减。

## 二、核心原理（用类比解释）

像一个**有经验的工程师调试代码**：

- 看到 timeout → 等一下重试（暂时性问题）
- 看到 "table not found" → 检查拼写，换个表名（参数问题）
- 看到 "permission denied" → 不重试，直接找运维（永久问题）

Agent 的反射机制就是把这个调试经验编码成规则：分类错误 → 给 LLM 结构化反馈 → LLM 修正参数或换方案。

## 三、反面案例 —— 如果没有它，会发生什么？

工具调用失败时，LLM 拿到裸错误堆栈（如 `ConnectionError: timeout after 30s`），可能出现：
- **盲目重试**：不断用同样参数调用同一个工具，陷入死循环
- **随意发挥**：编造一个结果替代工具返回，导致事实错误
- **上下文浪费**：每次失败都消耗一轮对话 token，连续失败快速耗尽窗口
- **任务失败率指数上升**：长任务（20+ 步）几乎必然在中途崩溃

## 四、我能用它做什么？（3 个具体场景）

1. **生产环境 Agent 服务**：对外暴露工具的 Agent 必须在工具层做错误分类+反射，否则用户一个拼写错误就能让 Agent 浪费几十次 LLM 调用
2. **多工具编排**：Agent 调用链中任一工具失败时，反射机制让 Agent 自主决定是重试、换工具还是降级给人类
3. **成本控制**：PERMANENT 错误立即停止（不浪费 token），降级阈值防止连续失败烧钱

## 五、和已有知识的关联

- **13 章 错误恢复接口**：当时在工具返回中嵌入"原因+可用选项+正确示例"，本章把它系统化为三分类+反射循环
- **16 章 Agent Memory**：Reflexion 论文的思路是把失败经验存入长期记忆，跨会话避免重复犯错——是本章反射机制的进阶版
- **12 章 ReAct**：反射是 ReAct 循环中 Observation 环节的增强——Observation 不再只是"结果"，还包括"失败原因+修正建议"
